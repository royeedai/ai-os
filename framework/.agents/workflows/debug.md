# /debug

当用户要求修复单一 bug、微调样式 / 文案 / 配置，或定位一个明确问题时触发。

## 目标

用最小但完整的流程完成"先定方案再动手"，避免越界修复和改 A 坏 B。

## 反模式：这个 Bug 太简单不需要方案确认

即使是最简单的 Bug，也需要最低限度的方案确认。"显而易见"的修复方案常常是错的——它可能修的是症状而不是根因，或者引入的改动超出了预期范围。

最小确认只需一句话：**"问题是 X，根因是 Y，我只改 Z 文件的这个位置，验证方式是 W"**。

如果连这一句话都说不出来，说明你还没有充分理解问题。

## 必做步骤

1. 读取 `.ai-os/STATE.md`、相关 `MISSION.md` / spec / 任务上下文，确认本次问题没有超出 `P2` 边界
2. 明确：
   - 复现路径或现象
   - 当前假设或已确认根因
   - 影响范围
   - 计划修改的文件和模块
   - 是否触及核心逻辑、已确认设计或关键依赖
3. 当现象跨越组件边界、共享包装层 / 转换层或全局样式基准时，先检查 request wrapper / interceptor、DTO / adapter、中间件、路由 / 鉴权或样式变量，再给出修复方案
4. 向用户输出修复方案、边界说明、风险和验证计划，禁止未定方案直接改代码
5. 等待用户明确回复"确认修复方案，可执行"
6. 只修改直接相关代码；若执行中发现问题超出原边界，立即暂停并升级到 `/change-request` 或 `/design`
7. 修复时遵循 TDD：先写一个复现该 Bug 的失败测试，确认测试因 Bug 而失败，再实施修复，确认测试通过
8. 完成后验证：
   - 目标问题已解决
   - 影响范围内相关功能已回归
   - 若仓库存在 compile / type-check / build 入口，至少执行并记录一项项目原生静态校验
   - 没有引入新的已知回归
9. 输出完整的验证结果与回归报告
10. 更新 `.ai-os/STATE.md`，必要时同步 spec / acceptance 中的验证记录

## 输出

- 修复方案与边界说明
- 修改后的验证和回归结论
- 是否需要升级为更高治理档位

## 禁止事项

- 禁止在未给出根因 / 假设、影响范围和文件边界前直接改代码
- 禁止顺手重构、统一风格或修改无关逻辑
- 禁止多个独立改动点混在一次修复里静默推进
- 禁止不做回归就宣称修复完成
- 禁止以"太简单"为由跳过方案确认步骤
- 禁止不写复现测试就修 Bug（除非确实无法自动化测试，需显式说明原因）
