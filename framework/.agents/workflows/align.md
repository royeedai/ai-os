# /align

当用户提出一个新项目、模糊想法、复刻目标、老项目需求变更，或任何“先把方向说清”的任务时触发。

## 目标

在开始设计和编码前，把以下内容说清并写入 `MISSION.md`：

- 项目目标
- 用户场景
- 范围边界（做什么 / 不做什么）
- 核心需求
- 非功能性约束
- 成功标准
- 验收基线
- 技术选型约束
- 现在属于哪种项目模式：`greenfield` / `reverse-spec` / `brownfield` / `change`
- 当前任务属于 `P0` / `P1` / `P2` 哪一档，以及推荐采用什么治理强度

## 必做步骤

1. 识别当前任务是项目级、模块级，还是局部变更
2. 判断当前任务治理档位：
   - 新项目 / 新模块 / 大范围变更：`P0`
   - 已有模块功能新增或非核心调整：`P1`
   - 单点 bug、文案、样式、配置微调：`P2`
3. 判断项目模式：
   - 从想法起步：`greenfield`
   - 参考截图 / API / 源码：`reverse-spec`
   - 先接手现有仓库：`brownfield`
   - 已有项目上的变更：`change`
4. 把用户提供的截图、接口文档、口头描述、现有代码、历史约束整理为结构化需求框架，并强制覆盖 8 个核心模块：
   - 项目目标
   - 用户场景
   - 范围边界（做什么 / 不做什么）
   - 核心需求
   - 非功能性约束
   - 成功标准
   - 验收基线
   - 技术选型约束
5. 为核心需求建立可追溯的需求点标识，确保后续可拆任务、可做验收、可留验证结论
6. 明确“当前最小可行闭环”和“可后续补充项”
7. 明确质量优先级：逻辑正确、关键体验、工程可维护、交付速度的先后次序
8. 明确关键技术栈、目标运行态、关键工程选型和不可逆方案，区分已确认与待确认
9. 主动识别素材中的模糊点、歧义点、默认假设和待确认边界，整理成问题清单，禁止脑补填空
10. 对出现“配置 / 设置 / 选项”的需求，轻量追问一次操作闭环：它是静态预置、后台可配，还是需要用户 / 运营入口
11. 生成或更新 `.ai-os/MISSION.md`，确保结构清晰、需求点可追溯、可拆解、可验收，并把配置闭环类澄清写进问题清单或范围说明
12. 生成或更新 `.ai-os/STATE.md`，记录当前阶段、当前目标、待确认项、确认停点和最小阅读集
13. 向用户输出 `MISSION.md` 核心摘要、当前治理档位、待确认项和下一步建议，等待用户明确确认后再离开 `/align`

## 输出

- `.ai-os/MISSION.md`
- `.ai-os/STATE.md`
- 向用户同步的需求摘要、问题清单和推荐路径：继续 `/design`、进入 `/change-request`，还是先补素材 / 先做 brownfield 结构梳理

## 禁止事项

- 禁止在目标、用户和成功标准不清时直接进入大规模实现
- 禁止把“用户一句话需求”自动脑补成完整产品定义
- 禁止在关键技术选型未确认时由 AI 默认拍板
- 对明确的局部改动，禁止默认先全仓分析
- 禁止未等待用户确认就直接推进到 `/design`、`/plan` 或 `/build`
