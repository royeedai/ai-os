# 代码交付前自审守卫

本 Skill 在模块开发完成后触发，对照 `.spec.md`、`.ai-os/tasks.yaml` 和 `.ai-os/acceptance.yaml` 验证实现是否完整。它不是"默认所有模块都走同一套重审流程"，而是先识别模块类型和交付档位，再做最低足够的质量审查。

## 使用时机

- 开发任务标记为"完成"前
- 用户要求"检查一下代码是否完整"
- 提交 PR / Code Review 前
- 用户说"这个模块做完了"

## 使用方式

1. 打开 `.ai-os/MISSION.md`、对应 `.spec.md`、`.ai-os/tasks.yaml`、`.ai-os/acceptance.yaml`、`.ai-os/verification-matrix.yaml`
2. 先识别模块类型（`页面类` / `API 类` / `数据处理类` / `工具类`）和交付档位（`exploratory` / `standard` / `high-risk`）
3. 按 Step 0 → Step 1 → Step 1.5 → Step 2 → Step 3 → Step 4 顺序推进；Step 0 未过直接判不合格
4. 仅在模块存在明显跨层联动时调用 `fullstack-dev-checklist`；其他按模块类型走专项
5. 若准备对外宣称"完成"，调用 `acceptance-gate` 出通过 / 阻塞结论；只有需要人工验证时才附 UAT 脚本

## 约束

- Step 0 未通过即判不合格，不进入后续
- 不把所有模块都自动升级为 `fullstack-dev-checklist`
- 本 Skill 负责模块级交付前自审，不替代项目规划、spec 编写或正式发布审批

---

## Step 0：工程完整性验证 [硬性前置]

**在任何逻辑审查前，先确认代码能编译、能运行、能访问。未通过直接判不合格。**

### 0.1 编译与入口

- [ ] 执行了项目级编译/构建命令且无错误（证据来自项目构建工具链，不是 IDE 内置诊断如 ReadLints）
- [ ] 若仓库存在 compile / type-check / build 入口，至少执行并记录了一项项目原生静态校验
- [ ] 按 `.ai-os/verification-matrix.yaml` 或 `verification_required` 执行了本次改动声明的动作；`restart_required` / `cold_start_required` 命中时已真实重启 / 冷启动
- [ ] 新模块接口处理器已注册到路由文件；服务链路已在主入口初始化；新 Model 已加入数据库迁移脚本
- [ ] 同一目录下无重复定义的结构体 / 类 / 函数；增量开发时新模块引用的旧 Model 已补全必要字段

### 0.2 项目脚手架与可运行性

- [ ] 前端骨架齐全（依赖声明 + 构建配置 + HTML 入口 + 应用初始化 + 根组件/布局 + 路由表）
- [ ] 后端骨架齐全（依赖声明 + 启动入口 + 路由注册 + 中间件）；开发模式鉴权旁路已就绪
- [ ] 容器化构建文件 + 环境编排文件可一键启动完整环境；前后端 API 代理配置匹配；HTTP 工具已封装错误处理 / Token 挂载
- [ ] 版本控制忽略规则文件存在
- [ ] 若项目存在目标运行态与开发 fallback 差异，已把 fallback 自测证据与目标运行态证据分开
- [ ] 若改动涉及共享包装层 / 转换层，已先核对 request wrapper / interceptor、DTO / adapter、中间件、路由鉴权或全局样式基准

### 0.3 横切基础设施 bean 全仓审计（新增 Java `@Configuration` / `@Bean` / `@ControllerAdvice` 前必执行）

> 范围：Jackson / Web MVC / GlobalException / Security / Mybatis-Plus / Cors / OpenFeign / Redis / MessageSource 等
> 详见 `framework/.agents/references/derived-rules.md` 4.9 节

- [ ] 新增前已搜索同类 bean 是否存在；**搜索范围覆盖所有 Java / 后端模块**（不得只搜 common / server / 印象中相关的几个模块）
- [ ] 已检索的模块清单在 debug 说明 / baseline-log / commit message 中显式列出
- [ ] 若已存在同类 bean：改为修改既有 bean / 明确放弃新增 / 在 commit 说明为何必须并存（三选一）
- [ ] 若 `.ai-os/CONVENTIONS.md` 有"全局基础设施 bean 清单"专节，已同步登记

**未通过 Step 0 的代码，直接判为「不合格」。**

## Step 1：spec 对照检查

逐一检查 `.spec` 中每个 FR-XXX：

```
对每个 FR-XXX：
  1. 功能已实现
  2. 交互流程与 spec 描述一致
  3. 模块类型对应的输入 / 输出 / 界面 / 命令契约完整，能支撑关键用户任务
  4. 状态处理 / 错误处理 / 权限边界已实现
  5. 边界条件和失败路径已处理
```

---

## Step 1.5：契约基准与弱类型洞双硬检查

> 契约不一致和弱类型洞是跨 session 飘走的两大主因。命中任一即视为实现质量门未通过。

### 1.5a 契约基准比对

- [ ] spec 声明了 `契约基准`、`字段映射/适配说明`、`集成触点`
- [ ] brownfield / change 任务若有共享基础设施约定，已在 spec / DESIGN / review 记录里写清
- [ ] 前后端、API / worker、DTO / entity、事件发布 / 消费之间的字段名、状态枚举、错误码、分页 / 过滤字段与 spec 一致；命名差异处 spec 显式声明映射、代码有 adapter / translator
- [ ] 若命中 `impact_tags` 的 `mapping` / `schema` / `state-transition`，已补兼容性和 degraded-path 证据
- [ ] MISSION / DESIGN 的技术选型（依赖名、版本约束、运行时版本）与实际构建配置逐项一致
- [ ] 若 `.ai-os/CONVENTIONS.md` 存在"跨层契约登记表"，本次实现与登记表一致（HTTP↔业务码映射 / Wire 类型契约 / 名单型常量真理源 / 敏感数据 service 方法语义档位 / 中间件方言五节）

### 1.5b 弱类型洞扫描（PL-034；详见 `derived-rules.md` 4.4 节）

| 反模式类别 | 硬检查项 | 合规出口 |
|---|---|---|
| 契约载体 | `Map<String,?>` / `JSONObject` / `dict` / 自由对象作为请求 / 响应体 | 仅透传 / 动态字段 / 第三方回调允许，需代码注释 + `memory.md` 技术债登记 |
| 契约载体 | 前端裸字符串动词（`request.get(path)`）无 method × path × requestDTO × responseDTO 类型校验 | 必须在类型层校验四元组 |
| 异常处理 | `catch (Exception)` + 笼统业务码包装不带 cause、不 log 堆栈 | 仅捕获可预期异常 / 传 cause / `log.error(..., e)` 三选一 |
| 字段定义 | DTO 字段无 service 层使用点 | 必须删除或显式保留注释（"前端回显" / "审计字段" / "兼容旧版本"） |
| 字段定义 | 前端 reactive / ref / state / store 业务字段在 DTO / spec / schema 三处均找不到（UI 自产字段） | 走 `/change-request` 落基线 / 从 UI 移除（二选一）；禁止挂着等后端 |
| UI 控件默认值 | 业务关键字段（ID / 金额 / 时间 / 精度敏感）使用带默认 `max`/`min`/`step`/ 精度 / 格式化的 UI 控件未显式覆盖默认值 | 必须显式声明覆盖 |
| UI 控件默认值 | ID 类字段（Long / BIGINT / Snowflake）使用会走 JS Number 的输入控件（`el-input-number` / `input[type=number]`） | 必须改为 `el-select` 等下拉 / 选择器 |
| 输入归一化 | 用户自由文本字段（SQL / 表达式 / JSON / 脚本）消费侧假设"上游会清洗" | 必须在 DTO 层或 service 入口声明归一化 owner |

## Step 2：按模块类型选专项

所有模块都必须检查的通用项：

1. **需求实现完整性**：spec、tasks、DoD、边界条件
2. **证据完整性**：构建 / 测试 / 运行 / 样例 / 日志满足当前档位
3. **业务逻辑合理性**：状态流转、约束、失败路径、回归影响
4. **用户任务可用性**：关键能力入口、执行链路、结果反馈真实成立
5. **双向溯源**：代码 ↔ spec / tasks / acceptance 一致

**按模块类型追加专项**：

| 模块类型 | 专项重点 | 默认不要求 |
|---|---|---|
| 页面类 | 页面完整性、UX、权限显示、导航可达性、关键交互、benchmark / 信息架构一致性、人工验证路径；涉及 API + 持久化联动时调用 `fullstack-dev-checklist` | — |
| API 类 | 契约、参数校验、错误处理、鉴权、幂等性、调用样例、回归；同时牵涉复杂页面 + 持久化时调用 `fullstack-dev-checklist` | 页面截图 / UAT |
| 数据处理类 | 输入输出契约、执行频率、日志、重试 / 补数 / 失败恢复、幂等性、结果样例 | 页面截图、列表页要素、完整 UAT |
| 工具类 | 命令参数、配置读取、帮助输出、退出码、安装 / 运行方式、结果输出 | 数据库设计、页面完整性、正式发布审批链 |

## Step 3：深度审计与专项

根据代码模块属性决定是否**强制调用**连带专项：

1. **命中高风险触发词族 / 涉及资产、权限流转、不可逆状态变更** → 立即启动 `security-guard`
2. **涉及复杂架构设计或大范围重构** → 立即启动 `architecture-reviewer`
3. **页面类或跨层联动业务模块** → 继续检查下列高频遗漏

### 3.1 页面层高频遗漏（参 `fullstack-dev-checklist` 维度一 + 维度四）

- [ ] 关键能力入口真实可达、可触发、可完成闭环（按钮 / 菜单 / 命令 / 手势 / 快捷操作都算入口），而不是静态展示、假入口或死链
- [ ] 从入口到结果反馈形成完整闭环，而不是只做局部页面或表面交互
- [ ] 关联数据选择器显示名称（而非 ID）；危险操作有二次确认弹窗（含对象名称）
- [ ] 表单提交成功后跳转回列表并刷新 + 防重复提交；数据格式化到位（时间可读、金额带单位、状态用标签、下拉有占位符）
- [ ] 文件上传全链路到位（前端组件 + 后端接口 + URL 返回）
- [ ] 企业后台页面符合 benchmark 和信息架构，避免完整新建表单和列表粗暴同屏做成 demo
- [ ] 若项目章程要求登录、角色 / 权限、组织 / 仓库上下文，这些入口和作用范围已体现

### 3.2 API 层高频遗漏

- [ ] 列表接口返回关联数据名称；创建 / 更新接口有完整参数校验；分页参数正确处理；错误响应统一格式
- [ ] **实际调用烟雾测试**：每个接口实际调用过一次（创建 / 查询 / 更新 / 删除 / 状态变更），**附实际请求响应日志作为证据**

### 3.3 回归影响

- [ ] 修改是否涉及共享代码（Model / 工具函数 / 中间件 / 共享组件）；若是，关联模块已重新编译 / 测试确认无影响
- [ ] 涉及共享运行时代码的关联服务已重启并完成冷启动验证
- [ ] 修复 Bug 时确认不会引入新问题

### 3.4 数据层高频遗漏

- [ ] 外键字段有索引；金额用定点数类型；软删除正确实现；事务在需要处使用

---

## Step 4：交付证据与验收门禁

- [ ] Evidence Pack 齐全（构建结果、测试结果、关键日志、截图、接口样例）
- [ ] 明确检查了"真实可用"而不只是"界面上看起来有"
- [ ] 分别给出了正常路径和 degraded-path（空值 / 缺字段 / 权限拒绝 / 超时 / 部分失败）的证据
- [ ] 本次变更要求 restart / cold-start 时，`restart-log`、`cold-start-log`、`post-restart-smoke-log` 齐全
- [ ] 分别判断了"最小可运行"和"可验收"，未把"能跑"直接写成"已完成"
- [ ] 明确区分 `AI 已完成` 与 `需人工执行`，把 SQL / 重启 / 迁移 / 补数 / 环境变更列入交付说明
- [ ] 未实现、未验证、仅占位或仅 demo 的能力明确排除在"完成"之外
- [ ] 若项目存在开发 fallback 与目标运行态差异，未用 fallback 证据替代正式运行态证据
- [ ] `.ai-os/tasks.yaml` 关键任务都附有完成证据；blocker 明确记录而不是模糊写成"待优化"
- [ ] 调用 `acceptance-gate` 给出最终通过 / 阻塞 / 建议优化结论；需要人工验证的模块附 UAT 脚本

## 档位缩放（交付等级决定审查深度）

| 档位 | 必须 | 可省 |
|---|---|---|
| exploratory | Step 0 工程完整性 + 关键结果证据 + 已知限制 / blocker 说明 | 完整九维度描述、正式发布级材料 |
| standard | Step 0 + 1 + 1.5 + 2 + 4；完整 spec / tasks / acceptance 对照；类型专项检查结果；用户可见模块的人工验证路径 | — |
| high-risk | standard 全部 + Step 3 安全 / 架构 / 发布 / 回滚准备 + degraded-path；对外发布时与 `release-manager` 结论保持一致 | — |

## 验收报告模板

```markdown
# 验收报告：[模块名]

## 基本信息
- **模块名称**：[名称]
- **.spec 文件**：[路径]
- **审查日期**：[日期]
- **总体评分**：[X/10]

## spec 对照结果

| FR 编号 | 功能描述 | 实现状态 | 备注 |
|---|---|---|---|
| FR-001 | [描述] | ✅ 完整 | |
| FR-002 | [描述] | ⚠️ 部分 | [缺少什么] |
| FR-003 | [描述] | ❌ 未实现 | [原因] |

## 审查结果

| 维度 / 专项 | 完成度 | 关键发现 |
|---|---|---|
| 工程完整性（Step 0） | 100% | 编译通过、入口齐全、横切 bean 审计已做 |
| 契约 + 弱类型洞（Step 1.5） | 95% | 跨层登记表对照通过、弱类型洞无命中 |
| 类型专项检查（Step 2） | 90% | [按页面 / API / 数据处理 / 工具填写关键发现] |
| 证据完整性（Step 4） | 85% | [缺少什么证据] |
| 双向溯源 | 80% | 部分核心逻辑缺少 spec 注释 |

## 遗漏项清单

### 必须修复（阻塞交付）
1. [ ] [具体描述]

### 建议优化（不阻塞但应改进）
1. [ ] [具体描述]

## 人工验证脚本（UAT，可选）

> 以下由 `acceptance-gate` 自动生成，详见其 SKILL.md 中的 UAT 模板。

## 结论
- [ ] ✅ 通过验收，可交付
- [ ] ⚠️ 需修复上述必须项后重新验收
- [ ] ❌ 多处关键功能缺失，需要重构
```
