# Payment Callback Design

## 1. 设计目标

- **本轮设计目标**：锁定支付回调主链路与 degraded-path 处理策略
- **需要先锁定的关键页面 / 交互**：回调接收、状态更新、异常记录
- **必须用户确认的核心设计决策**：超时订单和已关单订单的处理策略
- **允许 AI 自行处理的非核心细节**：日志字段命名
- **允许后补的细节**：退款回调联动

## 2. 信息架构

- **入口与导航骨架**：支付网关回调入口 -> 订单状态机
- **一级 / 二级结构**：回调校验 -> 状态判断 -> 更新 / 审计
- **关键上下文切换点**：状态更新前后
- **关键信息优先级**：回调真实性 > 状态一致性 > 审计信息

## 3. 关键页面与交互

| 页面 / 入口 | 目标 | 关键元素 | 关键操作 | 是否核心决策 | 确认状态 |
|-------------|------|----------|----------|--------------|----------|
| 回调处理入口 | 正确处理支付回调 | 验签、状态机、审计 | 接收 / 校验 / 更新 | yes | pending |

## 4. 关键流程

1. 接收支付网关回调
2. 验签并校验请求体
3. 根据订单当前状态决定是否更新
4. 记录异常、重复和超时路径

## 5. 视觉方向

- **视觉参考**：不适用，以系统行为为主
- **信息密度 / 布局原则**：审计和结果优先
- **组件与交互风格**：不适用
- **明确不采用的风格**：不在本轮补 UI
- **与既有设计系统或参考对象的差异**：无

## 7. 差异与待确认项

- **相对参考对象的明确差异**：本轮只覆盖支付回调，不做退款回调
- **仍待确认的设计项**：已关单后收到成功回调的策略
- **执行边界与非目标**：不扩展支付发起和对账

## 8. 方案选型依据

- **为什么选择当前方案**：先把异常路径前置锁定，避免 happy path 伪完成
- **备选方案与放弃原因**：只做成功回调无法满足交付质量门
- **与需求基准的对应关系**：直接对应成功、失败、超时、重复路径

## 9. 核心约束

- **必须遵守的技术 / 产品约束**：沿用现有订单状态机
- **共享基础设施约定**：回调验签与审计链路需保留
- **不可越过的范围边界**：不改支付发起流程
- **依赖前提**：超时和关单策略已确认

## 10. 风险与注意事项

- **主要风险**：重复回调、网络抖动、已关单状态误更新
- **注意事项**：degraded-path 必须逐条留证据
- **触发升级到 change-request / review 的条件**：需要改订单状态机或补偿策略
