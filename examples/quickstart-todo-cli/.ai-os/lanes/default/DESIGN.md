# Design

## 1. 设计目标

用最少代码实现可靠的本地 Todo CLI。

## 2. 信息架构

- 单一入口 `todo` 命令
- 子命令：`add <text>`, `list [--all|--done|--pending]`, `done <id>`, `delete <id>`

## 3. 关键页面与交互

### 命令结构

```
todo add "买牛奶"          → 添加任务，输出 ID
todo list                  → 列出待办任务
todo list --all            → 列出全部任务
todo done 3                → 标记 #3 为完成
todo delete 3              → 删除 #3
```

### 输出格式

```
  #1 [ ] 买牛奶
  #2 [x] 写周报
  #3 [ ] 修 bug
```

## 4. 关键流程

1. 读取 ~/.todo.json（不存在则创建空数组）
2. 执行命令操作
3. 写回 ~/.todo.json
4. 输出结果

## 5. 视觉方向

纯文本终端输出，`[x]` 表示完成，`[ ]` 表示待办。

## 8. 方案选型依据

- **为什么选择当前方案**：quickstart 需要最小但完整的本地 CLI 闭环，零依赖 JSON 存储最适合作为主路径示例
- **备选方案与放弃原因**：SQLite / 远端 API 会引入额外运行态和部署复杂度，不适合作为入门示例
- **与需求基准的对应关系**：直接覆盖 `add/list/done/delete`、本地持久化和异常提示

## 9. 核心约束

- **必须遵守的技术 / 产品约束**：零运行时依赖、单用户本地 CLI、JSON 文件可直接读写
- **共享基础设施约定**：无统一 wrapper / adapter；命令入口直接调用文件存储层
- **共享层 / 通用抽象副作用清单**：本例无 shared layer / BaseEntity / Router Guard / 多租户上下文；若后续引入统一存储层，需重新评估文件格式兼容性和命令输出兼容性
- **路由 / 入口契约对照**：唯一入口为 `bin/todo.js`，子命令名称与 spec 命令表一一对应
- **Schema / 存储一致性说明**：`~/.todo.json` 的持久化结构必须保持 `{ id, text, done, createdAt }`
- **同仓正常实现对照**：`src/store.js` 与 `src/commands.js` 是本例唯一对照实现，后续扩展需保持其契约
- **不可越过的范围边界**：不引入多用户、远端同步或复杂标签系统
- **依赖前提**：本地文件系统可读写用户 home 目录

## 10. 风险与注意事项

- **主要风险**：手工修改 JSON 文件导致结构损坏；home 目录权限不足导致写入失败
- **注意事项**：扩展命令前先补 spec / tasks / acceptance，不要直接修改 CLI 输出格式
- **触发升级到 change-request / review 的条件**：引入远端同步、并发写入、共享存储或统一包装层
