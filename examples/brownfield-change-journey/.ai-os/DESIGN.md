# Brownfield Change Design

## 1. 设计目标

- **本轮设计目标**：为次数限制变更锁定提示方式、拦截位置和影响边界
- **需要先锁定的关键页面 / 交互**：触发限制后的提示与拦截反馈
- **必须用户确认的核心设计决策**：提示文案与拦截行为
- **允许 AI 自行处理的非核心细节**：局部实现命名
- **允许后补的细节**：限制策略配置化

## 2. 信息架构

- **入口与导航骨架**：沿用现有用户操作入口
- **一级 / 二级结构**：不新增全局导航
- **关键上下文切换点**：触发限制前后
- **关键信息优先级**：限制原因 > 剩余可操作信息

## 3. 关键页面与交互

| 页面 / 入口 | 目标 | 关键元素 | 关键操作 | 是否核心决策 | 确认状态 |
|-------------|------|----------|----------|--------------|----------|
| 触发限制入口 | 拦截超额操作 | 限制提示、剩余次数 | 提示 / 阻止 | yes | pending |

## 4. 关键流程

1. 用户触发受限操作
2. 系统检查次数限制
3. 超限时阻止操作并给出提示
4. 不影响其他模块链路

## 5. 视觉方向

- **视觉参考**：沿用现有 Web 系统提示样式
- **信息密度 / 布局原则**：不新增复杂 UI
- **组件与交互风格**：沿用已有 toast / inline warning
- **明确不采用的风格**：不新增独立管理页
- **与既有设计系统或参考对象的差异**：仅做局部提示增强

- 2026-03-18：确认这是局部变更，不扩展成全局重构
- 2026-03-18：待确认提示样式和拦截方式

## 7. 差异与待确认项

- **相对参考对象的明确差异**：不新增配置后台
- **仍待确认的设计项**：提示出现位置与文案
- **执行边界与非目标**：不改其他模块

## 8. 方案选型依据

- **为什么选择当前方案**：优先锁定影响边界，避免 brownfield 扩散
- **备选方案与放弃原因**：全局重构成本高且越界
- **与需求基准的对应关系**：直接对应次数限制规则与提示

## 9. 核心约束

- **必须遵守的技术 / 产品约束**：沿用现有技术栈和 API
- **共享基础设施约定**：先审计共享拦截、DTO 和接口包装
- **不可越过的范围边界**：不动其他模块
- **依赖前提**：变更范围已确认

## 10. 风险与注意事项

- **主要风险**：局部改动扩散为全局行为变化
- **注意事项**：先确认共享基础设施约定
- **触发升级到 change-request / review 的条件**：需要影响多个模块或新增配置入口
