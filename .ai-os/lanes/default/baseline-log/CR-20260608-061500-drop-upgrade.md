## Trigger

Project owner asked to read the whole project, remove ambiguity / errors / historical baggage, and keep only "latest install works well". The largest baggage was the `upgrade` command plus the v7/v8 migration machinery (legacy layout detection, root-only / hybrid normalization, `.agents/` cleanup) — code paths that only serve users migrating from pre-v9 layouts, which the owner explicitly no longer wants to support.

## Current behavior

- `create-ai-os` exposed 3 primary operations: install / doctor / upgrade.
- `bin/ai-os-upgrade.js` (435 lines) + `shared.js` legacy helpers (`detectLayout`, `normalizeLaneToml`, `readKeyValueToml`, `inferQualityTier`, `inferRiskTier`, `ROOT_ONLY_LEGACY_*`, `LAYOUT_MODE_ROOT_ONLY/HYBRID/UNKNOWN`) migrated v7/v8 layouts into v9 canonical.
- `doctor` ran `detectLayout` and emitted `E060` / `E061` / `W060` to push users toward `upgrade`; per-artifact checks were gated on layout mode.
- Docs (README / cli / getting-started / constitution-spec / maintainers / PROJECT_PURPOSE) and `migrate-to-v9.md` documented the upgrade path.

## Proposed delta

- Delete `bin/ai-os-upgrade.js` and the upgrade subcommand route; remove the legacy-only constants/functions from `shared.js`.
- Converge `doctor`: drop `checkLayout` + E060/E061/W060 + `detectLayout`; run per-artifact checks unconditionally; read `layout_mode` from `framework.toml`; W002/E002 point to a fresh `install . --force`.
- Delete `docs/migrate-to-v9.md`; rewrite docs to 2 operations; de-version user-facing "AI-OS v9" wording (layout schema stays `9`).
- Fix confirmed audit issues: mcp-resources dead link → standards-map; BL-template W073 line; problem-ledger PL ordering (012→015) + constitution-spec anchors (→v2.0) + PL-007/PL-019 anchors; ide-pointers route through Activation Gate; lane MISSION quality/risk split; tasks.yaml `scope.quality_tier`; eval-example frontmatter; 3 evals re-grounded on current `tasks.yaml` schema.
- Bump to 10.0.0; add CHANGELOG 10.0.0 entry; sync `.cursor/rules/project-lead.mdc`.

## Preventability review

- **Preventable**: no
- **If yes, root cause**: n/a — `upgrade` was a reasonable one-time migration tool across the v7→v8→v9 transitions. Removing it is a deliberate surface-convergence decision made by the project owner ("only the latest install needs to work well"), not rework caused by a missed question, unlocked design, or unconfirmed scope in a prior AI-OS delivery.
- **Maps to**: PL-007 (default-layout truth-source divergence) — dropping `upgrade` shrinks the legacy surface so install / doctor / docs / tests express a single fresh-install truth; tightens single-source-of-truth and relieves PL-009 (progressive disclosure) by removing legacy detection code agents would otherwise reason about.
- **Suggested guard**: hold the "no new CLI subcommand" red line in reverse too — keep the operating surface minimal; if legacy migration is ever needed again, ship it as a standalone one-shot script or doc, not a resident CLI command. When product version and layout-schema version diverge (product 10 vs schema 9), state the relationship explicitly in CHANGELOG to avoid v9/v10 ambiguity.
